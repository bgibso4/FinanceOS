Pending transactions

Bank sync brings in pending charges from Plaid accounts, but nothing marks them as pending. When a charge posts, Plaid sends it as a brand-new transaction and tells us to remove the pending one. So the category, notes, tags, trip and splits you added are deleted, and you have to redo them a few days later. This keeps your edits: when a charge posts, the transaction you already have is updated in place instead of being replaced. A quiet "· Pending" note in the list and a short notice in the drawer show which charges are still waiting.

Waiting on you

These were my calls. You approved all four on 2026-11-22.

  • M1Your merchant name stays
    When a charge posts, it takes the bank's final date and amount but keeps the merchant name already on the transaction. You or a rename rule may have cleaned that name up, and we can't tell whether you did, so keeping it is the safe choice. Plaid's names for pending and posted charges are usually the same anyway.
    Posting
  • M2Splits that stop adding up are left as they are
    If the amount changes when the charge posts (a tip, a gas-station hold) and the transaction is split, the split parts are left alone. The split editor already shows when parts don't add up, so you fix it there. Splitting a pending charge is rare.
    Posting
  • M3Removals wait until the whole sync has run
    Plaid can send the "remove pending" message on an earlier page than the posted charge. If we acted on it right away, we'd delete the row before we could carry it over. So sync collects removals and applies them at the end, once every posted charge has had a chance to take over its pending row. A row that was taken over has a new ID by then, so the removal finds nothing to delete.
    Posting
  • M4No backfill for rows already in the app
    Pending rows synced before this change won't show "· Pending". They'll still be carried over when they post, because the link is through Plaid's IDs, which those rows already have. They'll be posted within a few days anyway.
    Data

Scope

Goals

  • Edits made to a pending charge survive when it posts
  • You can see which charges are still pending
  • Holds that never post are still removed

Non-goals

  • Teller accounts. They already skip pending charges, so nothing changes there.
  • A "posted only" filter in Analytics
  • Backfilling the pending flag on rows already in the app

Anti-goals

  • A posted charge showing up twice (the pending row plus a new one)
  • A label that crowds busy rows
  • Quietly overwriting a merchant name you edited

Approaches

1 · The pending flag

  • New field Transaction.isPending Boolean @default(false), applied with prisma db push. migrate dev fails on this database.
  • Plaid sync sets it from plaidTx.pending when it creates a transaction, and again whenever Plaid sends a "modified" update.
  • Manual entries, CSV imports, Teller and Splitwise imports always leave it false.
  • The cloud-sync payload carries the field (types.ts plus the export and import in sync.ts, the same way isOutsideBudget is handled), so another device shows it too.
  • Transaction API responses include it, so the list and drawer can read it.

2 · When a charge posts

  1. A new transaction arrives that has a pending_transaction_id. Before any other duplicate check, sync looks for a transaction in that account whose externalId equals that ID.
  2. If it finds one, that transaction is updated in place. The posted ID goes in externalId, along with the posted date, amount and a new importHash, and isPending is set to false. Category, confidence, note, tags, trip, outside budget, transfer pairing, refund links and split parts stay as they are. The merchant name stays too (M1). This counts as "merged" in the sync stats.
  3. If it finds none (the pending charge was never synced, or was outside the window), the existing path runs as usual: duplicate checks, then a new transaction.
  4. Removals are collected over the whole sync and applied at the end (M3). A removal whose ID still matches a row deletes it, as it does today. That covers holds that never post.
  5. The dry-run preview follows the same steps, so it shows "would merge" for a charge that will take over its pending row.

3 · List and drawer

  • TransactionTable: a pending row reads Merchant · Pending, with the suffix in muted text. It comes after "· Outside budget" when both apply, and before the Split label. Category, colours and amount are unchanged.
  • Drawer: under the amount, a muted notice on --bg-elevated with a small dashed accent dot. It reads: Pending. "The bank may still change the amount or date. Your category, notes and tags will carry over when it posts." It disappears once the charge has posted.
  • Everything in the drawer stays editable. Analytics, budgets and the review queue treat pending rows like any other transaction (A2, A4).

Left to the builder

  • Where the posting step sits in processPlaidTransaction: one helper, used by both the real sync and the preview.
  • How removals are collected across pages: an array of { transactionId, accountId } drained after the loop is enough.
  • If a unique-constraint race happens while taking over a pending row, treat it as "skipped", like the existing merge paths.
  • Which drawer component gets the notice: the header area of the shared TransactionDrawer.

Testing

  • Sync (mock the Plaid client the way the existing sync tests do):
    • A pending charge is created with isPending true.
    • When the posted charge arrives with pending_transaction_id, the same row is updated: same id, the new externalId, date and amount, the category, note, tags and trip kept, isPending false. There are no duplicates.
    • A "remove pending" that arrives on an earlier page than the posted charge still ends with one row that kept its edits.
    • A hold that's removed with nothing replacing it is deleted.
    • A posted charge whose pending row is unknown is created as before.
  • Cloud sync: isPending round-trips.
  • Component: the suffix shows only for pending rows, and the drawer notice only for pending transactions.
  • In the browser, both themes: the list suffix on a busy row, and the drawer notice.

Splitwise import

Shared expenses stop being typed in by hand. You download a group's or friend's export from splitwise.com and drop it on Settings → Import; FinanceOS reads only your column and imports at once into one Splitwise account. The same card then lists what that import did in the normal transaction table, where you fix categories and trips with the shared drawer or the bulk bar. Re-importing the same group later picks up only what changed in Splitwise: new rows, edited amounts, deletions. Everything an import did can be undone.

Waiting on you

My own calls. Each is easy to change now; veto any you don't like.

  • M1What counts as the same row
    A row's fingerprint is date, description, total cost and your amount. Identical fingerprints are counted, so two identical "Laundry $50" rows stay two. A row whose fingerprint is gone but whose date and description reappear once with a new cost or amount is an edit. Anything ambiguous (two candidates) is treated as a delete plus a new row, never guessed.
    Matching
  • M2Which group a file belongs to
    Splitwise names exports <group>_<date>_export.csv. The part before the date is the group. The card shows it ("trip-pair") on the first import of a group so a renamed file can be corrected. A friend export is assumed to follow the same pattern; check it when you first download one.
    File
  • M3Category: your rules, then a small fallback
    The description goes through your rules (autoCategorize) like any import. When no rule matches, a fixed map turns Splitwise's own category into yours: Hotel → Lodging, Taxi → Rideshare, Parking → Transportation, Groceries → Groceries, Dining out → Restaurants, Gas/fuel → Gas, Entertainment → Entertainment, Sports → Sports and Recreation. Anything else (General, Rent, Furniture…) arrives uncategorized and lands in the review queue.
    File
  • M4Payments are transfers
    Rows Splitwise files under "Payment" (e.g. "Ben G. paid …") import marked as transfers, not spending. The import itself changes nothing in other accounts: pairing with the Venmo or bank payment is left to the existing transfer detection when it next runs. Deleting a paired row later (Splitwise delete or Undo) unpairs its partner the way deleting any transfer already does.
    File
  • M5Splitwise wins on the amount
    An edit in Splitwise updates the amount (and date) on the existing transaction. Your category, trip, tags, note and links are kept. Exception: a transaction you've split in FinanceOS isn't changed automatically; it's flagged "Changed in Splitwise · check the split" so you fix the split yourself.
    Matching
  • M6Restore means "keep it"
    Restoring a row that was deleted in Splitwise brings the transaction back and marks it kept, so the next import doesn't delete it again.
    Undo
  • M7Only the latest import can be undone
    Each import builds on the one before, so Undo is offered on a group's most recent import only. Undoing it also makes FinanceOS forget that import, so the next file is compared with the one before it.
    Undo
  • M8One currency per account
    Rows whose currency differs from the Splitwise account's (USD) aren't imported; the summary counts them as "different currency" so nothing vanishes silently. Every row in your three exports is USD.
    File
  • M9Your name and account are remembered
    The card's "Into [account] as [name]" defaults to the last values used (first time: the account whose institution is Splitwise, and your name). If the file has no column with that name, the import stops and lists the names it found.
    Screen
  • M10Rows you've reshaped aren't deleted automatically
    If Splitwise deletes a row whose transaction you've split, linked to a refund or offset, or that is paired as a transfer, FinanceOS doesn't delete it. It's listed as "Deleted in Splitwise · check" with a Delete button, like M5's split edits. So Restore and Undo only ever rebuild plain transactions.
    Undo
  • M11You deleted it, it stays deleted
    If you delete an imported transaction yourself (drawer or bulk bar), its remembered row becomes "deleted by you". Later imports never re-create it, even if Splitwise edits it; the summary counts it as ignored.
    Matching

Agreed with you

From the brainstorm, the API check and the mock rounds.

  • A1CSV export, not the API
    Splitwise's API now needs Pro (about $40 a year); "too much". Exports are free and carry everything needed except IDs.
    File
  • A2One Splitwise account
    Everything goes into one account (you're renaming the existing shared account to "Splitwise"): the day-to-day tally, trips with your partner, and group trips. Its balance is your total across them.
    File
  • A3Only your column
    Other people's expenses and payments (your column 0.00) are skipped. Simplify-debts doesn't matter: only your own column counts.
    File
  • A4Amount is your column as is
    Negative when someone else paid (your share), positive when you paid (what others owe you). Same signs as the rows you type today.
    File
  • A5Import first, review after
    Dropping a file imports at once. No preview step, except one question on a group's first import.
    Screen
  • A6Edit in place with the shared pieces
    The card becomes this import's rows in the normal transaction table; a row opens the shared drawer; Select gives the bulk bar. "Just reuse the transaction sidebar."
    Screen
  • A7Re-imports pick up changes
    The next file of a group is compared with the last: new rows import, edits update in place keeping your changes, deletions are removed with a Restore button.
    Matching
  • A8Hand-typed history stays
    The rows already typed into the existing shared account stay as they are. A group's first import can skip rows before a date; those rows are remembered as skipped and never come back as new.
    Matching
  • A9Undo this import
    The safety net that replaces a preview: it asks inline, says what it will revert, then reverts it.
    Undo
  • A10Reuse, and prove the matching
    Principal-engineer rules: reuse existing components and code paths first. The matching must be proven correct by tests built from real exports.
    Testing

Scope

In

  • A Splitwise card on Settings → Import
  • Group and friend exports, any number of people
  • New, edited and deleted rows on re-import
  • Skip-before-date on a group's first import
  • Edit in place: shared table, drawer, bulk bar
  • Restore a deleted row; undo an import

Out

  • The Splitwise API and automatic fetching
  • Settling up or writing anything to Splitwise
  • Converting other currencies
  • Replacing the hand-typed history
  • Renaming the existing shared account (you'll do it)

Anti-goals

  • A row imported twice
  • A change applied that you can't undo
  • A second drawer or a second table
  • Anyone else's numbers in your account

Constraints

  • The repo is public. Test fixtures are made from your exports with names replaced (Person A, Person B…) and no real group names. Your real files stay in Downloads.
  • Vendor names only at the edge. "Splitwise" appears in the import's own module, its route and the card. Shared code (table, drawer, bulk bar) stays vendor-free.
  • Dates never convert. A Splitwise date is a calendar date, stored like any imported transaction date.
  • The usual rules: prisma db push, never migrate; the live database changes only with you, after a backup; tests never touch prisma/dev.db; the import writes only to the chosen account (M4).
  • Cloud sync carries the new tables, like it carries other data.

1 · Reading an export

What a Splitwise export looks like, from your three files.

  • Header: Date,Description,Category,Cost,Currency, then one column per person. A blank line follows the header; a final "Total balance" row follows a blank line at the end. Neither is an expense.
  • Quoting: descriptions can contain commas inside quotes ("Friday Dinner (Feb 13, 2026)"), and trailing spaces. The parser must handle real CSV quoting.
  • Your column is how much your balance moved. That is the transaction amount, unchanged. Rows where it is 0.00 are not yours.
  • Payments have category Payment. Someone can also record a settle-up as an ordinary expense ("Settle all balances", General); that imports as an expense like any other, which is what Splitwise says it is.
  • A settled group sums to zero in your column, which matches the file's "Total balance" row. The card shows that total as a check.
  • Transaction fields: merchant = the description (trimmed), date = Date, amount = your column, account = the chosen one, category per M3, transfer flag per M4. Total cost and Splitwise's category aren't transaction fields; the import keeps them on its own records and shows them under the description in the list.

2 · Matching and edits

The heart of it. Splitwise exports carry no IDs, so FinanceOS remembers every row of yours it has seen per group.

  1. Remember. Every row of yours from an import is stored per group with its fingerprint (M1) and what happened to it: imported (linked to its transaction), skipped by date, kept after a Splitwise deletion (M6), or deleted by you (M11).
  2. Compare. The next file of the group is compared with those rows. Exact fingerprint matches are unchanged, whatever their status, so a skipped row never returns as new.
  3. Edits. Of what's left, a vanished row and a new row with the same date and description, one each, are an edit: the transaction's amount (and cost) update, everything you set stays (M5).
  4. New and deleted. Remaining new rows import. Remaining vanished rows that were imported have their transaction deleted, shown under "Deleted in Splitwise" with Restore. Vanished rows that were skipped are simply forgotten.
  5. First import of a group. One question first: "Import everything" (default) or "Skip rows before [date]". Skipped rows are remembered as skipped.
  6. Same file twice is a no-op import: everything unchanged, nothing created.
A known limitAn edit that changes both the date and the description can't be recognised. It shows as one deleted row and one new row next to each other; the new one gets a fresh category.

3 · The import screen

Settings → Import gets a Splitwise card above the existing per-account CSV import, which is unchanged. Follow the mock.

  • Ready: "Import a Splitwise export", the file picker, and "Into [account] as [name]" (M9).
  • First import of a group: the group name, the file's people and row counts, the skip-before question, and an Import button.
  • After import: "Imported trip-pair · today 3:12 pm", Import another file, Undo this import. Summary chips: new (with payments), changed, deleted, unchanged, skipped by date, not yours, different currency, need a category.
  • The rows this import created or changed, in TransactionTable: badge New / Changed in Splitwise (old amount struck through) / Payment, with total cost and Splitwise's category under the description. Clicking a row opens the real shared drawer; edits save the way they do everywhere.
  • Select turns on the table's select mode and the bulk bar: set category, set trip, add or remove a tag, delete.
  • Below: "Deleted in Splitwise" rows with Restore; "N rows don't involve you" (expandable list); the group-balance check.
  • Leaving and coming back shows the card ready for a new file. The imported rows are on Transactions like any others.
  • Errors say what's wrong and what to do: not a Splitwise export, no column for your name, empty file, a failed save (nothing written).

4 · Restore and undo

  • Restore recreates a deleted transaction as it was (amount, category, trip, tags, note) and marks the row kept (M6).
  • Undo this import confirms inline, naming the counts ("removes 24 transactions, puts 1 changed row back to its old amount, restores 1 deleted row; edits you made to them are lost"), then reverts all of it and forgets the import (M7).
  • Both are all-or-nothing: a failure changes nothing.

5 · Engineering

Reuse first. Each new piece has one job; the two that decide things are pure and tested without a database.

PieceJob
CSV parsingOne quote-aware parser shared with the existing per-account import, whose comma split breaks on quoted fields today. No second parser.
Export readerPure: export text + your name → group, people, your rows (date, description, Splitwise category, cost, currency, your amount). Rejects files that aren't Splitwise exports.
MatcherPure: remembered rows + new rows → a plan of unchanged, edited, new and deleted. All of section 2 lives here.
Import serviceApplies a plan in one database transaction: creates through the same categorisation path as other imports, updates, deletes, records what it did for Undo. Writes only to the chosen account (M4).
StorageNew tables for imports and remembered rows (and whatever Undo needs). Only the service's store touches them.
RoutesImport a file, list an import's rows, restore a row, undo an import. Zod-validated, under /api/import/splitwise.
Bulk barLifted out of the Transactions page into a shared component used by both, gaining "Set trip" (the bulk route gains tripId). One bulk bar, not two.
CardA new component under the Import tab, built from TransactionTable, the shared drawer and the bulk bar. The 4,600-line Settings page only renders it.

Testing

Matcher (pure)

  • Same file twice → all unchanged
  • Added row → new; deleted → deleted
  • Changed cost or amount → edited
  • Identical repeats counted
  • Date and description both changed → delete + new
  • Two edit candidates → delete + new
  • Skipped rows never come back as new

Reader and service

  • Quoted commas, blank lines, total row
  • Rows not yours skipped; payments are transfers
  • Missing name column → clear error
  • Other currency counted, not imported
  • Edit keeps category, trip, tags, note
  • Split transaction flagged, not changed
  • Restore, then re-import: stays
  • Undo reverts creates, edits and deletes
  • Failure mid-import writes nothing

Component

  • First import asks; later imports don't
  • Summary chips match the result
  • Row opens the shared drawer
  • Select + bulk bar sets category and trip
  • Undo confirms inline, then reverts
  • The existing CSV import still works

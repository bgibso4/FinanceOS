Automatic sync and daily exchange rates

You stop clicking Sync. While the production server is running, it syncs every connected bank and investment account on its own, refreshes investment prices, and records the CAD→USD rate for the day in the same pass. Every transaction converts at the rate for its own date, so history stops moving when the rate does. The Sync buttons stay for when you want it right now.

Scope

Goals

  • Banks and investments sync on their own while the production server runs
  • The CAD→USD rate refreshes on its own, one rate per day
  • Past amounts convert at their own day's rate, so history stays put
  • You can tell when it last ran, and when something needs you

Non-goals

  • Syncing while the laptop is off (that's the Cloudflare project)
  • Notifications, emails, pop-ups
  • Changing how a sync works inside, or its deduplication
  • Currencies beyond those your accounts use
  • Storing a converted amount on each transaction
  • The server pushing cloud backups itself

Anti-goals

  • A dev server or test touching real bank connections
  • Two syncs of the same account running at once
  • One failing bank stopping the rest
  • Last year's totals changing because today's rate changed
  • The app slowing down or blocking pages while it syncs

Constraints

  • One sync path. The scheduler, the Sync buttons and "Sync all" run the same server code. No second copy of the sync or grouping logic.
  • Plaid items sync once per item. As "Sync all" already does: one sync per Plaid item or Teller enrollment, not per account, or the shared cursor advances on the first call and the rest import nothing.
  • The existing locks hold. withSyncLock per account or enrollment, and investments:refresh for prices, so a manual click during a pass waits rather than clashes.
  • Vendor names only at the edges (Plaid, Teller, Yahoo); neutral words elsewhere.
  • Tests never touch prisma/dev.db, and never call a real bank or price provider.
  • Design tokens only, light and dark, for the Settings and side-nav changes.

1 · When it runs

  • The production server starts a scheduler once when it boots. Every 15 minutes it checks whether the last pass finished more than 4 hours ago, and if so starts one M2.
  • The time of the last pass is stored in the database, so restarting the server doesn't trigger an extra pass if one just ran.
  • A sleeping laptop just delays the check. On wake, the next check sees the pass is overdue and runs it.
  • After any time down (off, asleep, server stopped), that first pass fills every missing day's rate from the last stored day up to today before syncing accounts, so transactions that arrive for those days convert at their own day's rate.
  • Only one pass at a time. If one is still running at the next check, that check does nothing.
  • Off in development and tests, and off in production when the environment switch says so M3.
  • Running in the background never blocks a page request.

2 · What a pass does

In this order. Each step stands alone: a failure is recorded and the pass moves on.

StepWhat happens
1 · RateFetch CAD→USD and save it (section 3).
2 · AccountsFor each connected Plaid item and Teller enrollment, one after another, run the same sync the Sync button runs, over 30 days M6, with no preview M8. This covers bank transactions and investment holdings and trades. Connections that already need a re-login are skipped, so they don't keep failing.
3 · PricesRefresh investment prices and valued balances, as Investments' Refresh button does M7.
4 · RecordSave when the pass finished and whether any step failed.
Cloud backupThe encrypted cloud backup runs in the browser, so a pass while no FinanceOS tab is open is backed up the next time you open the app. You agreed that's fine A7; the server doesn't push backups itself.

3 · Daily exchange rates

Today there is one CAD→USD rate and every conversion uses it, past ones included, so your 134 CAD transactions are all priced at whatever the rate is now. This changes to a rate for each day.

Where the rates come from

  • Source: Yahoo Finance's CADUSD=X, through the existing price provider M1.
  • Each pass records today's rate. Today's row is updated through the day; once the day is over it is fixed.
  • A one-time backfill pulls the daily history from the first CAD transaction or balance onward, the same way security price history is backfilled. A pass also fills any days that are missing, so a laptop that was off for a week catches up.
  • The pairs come from the currencies your accounts use and the base currency setting (CAD→USD today). No pair is hard-coded.
  • A fetch that fails or returns nonsense (zero, negative, or far from the previous day) writes nothing; the step counts as failed.

Which rate an amount uses

AmountRate
A transactionThe rate for its own date (spending, Analytics, Travel, Reports, budgets)
A past balance or snapshotThe rate for that day (net worth history, investment history)
A balance nowToday's rate (current balances, net worth, investments overview)
  • A day with no quote (weekend, holiday) uses the latest earlier day. A date before the history starts uses the earliest rate stored.
  • Transaction dates are calendar days, matched to the rate's calendar day, never converted (src/lib/dates.ts).

Settings

  • The rate shows read-only: "1 CAD = 0.7xx USD today · updated automatically · as of 2:14 pm", with a Refresh button M4. No hand-typed rate: the pass would overwrite it.

4 · Seeing it worked

  • Settings, where the connections are listed, gains one line: "Synced automatically · last run 2:14 pm · next around 6:15 pm". If the last pass had a problem, it names which step.
  • Each connection keeps its own last-synced time and status, as today, including "needs reconnect".
  • A small dot on Settings in the side nav when any connection's status says it needs a re-login, or the last pass recorded a failure M5. It's gone after a clean pass or once you reconnect.
  • The Sync buttons and "Sync all" stay as they are A5.

5 · Engineering

DRY > YAGNI > SOLID.

  • One sync per connection, in a library. The work the Plaid and Teller sync routes do moves into library functions the routes call. The scheduler calls the same functions directly, with no HTTP round trip to itself.
  • One grouping rule. The pass groups connections with the existing syncUnits (src/lib/sync-grouping.ts), and picks accounts the same way "Sync all" does. If that account selection lives in the Settings page, it moves into the library so both use it.
  • Re-login status moves with the sync. The error classification and the status write (Plaid needs_reauth, Teller disconnected) move from the route catch blocks into the library functions, so a pass records it too. The pass skips connections in either state.
  • Price refresh once per pass. The background price refresh the Plaid route fires after an investment sync stays in the route, not the library function. The pass runs its own single prices step.
  • One pass function. It runs the four steps in section 2 and returns a summary. The scheduler only decides when to call it. That makes the pass testable with fakes and lets the Settings Refresh button reuse the rate step.
  • The scheduler starts once per server, from Next.js's startup hook (instrumentation.ts, Node runtime only), guarded so a second registration does nothing.
  • The rate goes through the existing price provider, with the currency pair as a symbol, not a second client.
  • One conversion rule. The rate lookup gains a date: convertAmount / toBase take the day the amount belongs to, and loadCurrencySettings loads the daily rates for the range a caller needs. Every caller passes its date: analytics.ts, travel/totals.ts, the investments modules (current-holdings, overview, history, valuation), and the snapshots and accounts/balances routes. Callers about "now" pass today.
  • Rate storage. A rate per (pair, day). Whether that is the existing ExchangeRate table with a date added or a new table is the builder's call; the old single row becomes the first history point, not a second source. Schema changes go through prisma db push.
  • Figures still agree. The Analytics rule holds: chart, figures and breakdown convert the same rows with the same rule, so they still agree to the dollar.

Testing

Unit

  • Scheduler: due vs not due, skips while a pass runs, never starts in development or tests, honours the off switch
  • Rate: a good quote is saved; failures and nonsense values write nothing
  • Lookup: a transaction converts at its own day's rate; weekends use the earlier day; before history uses the earliest; "now" uses today
  • Grouping: one unit per Plaid item or Teller enrollment

Integration

  • A pass against a test database with fake providers: one failing connection doesn't stop the others, and the summary and last-pass record are right
  • Connections needing a re-login are skipped
  • The sync routes behave as before after the move into the library
  • Backfill fills history from the first CAD date and fills gaps, with a fake provider
  • Analytics and Travel totals for a past month don't change when today's rate changes

Component

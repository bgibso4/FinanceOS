Pending transactions: implementation plan

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Load the principal-engineer skill before writing code.

GoalEdits made to a pending Plaid charge survive when it posts, and pending charges show a quiet "· Pending" note in the list and a notice in the drawer.
ArchitectureOne boolean column, isPending, set by Plaid sync. When a posted charge carries pending_transaction_id, sync updates the existing row in place instead of creating a new one. Removals are collected across all pages and applied after the loop, skipping any pending ID a posted charge took over.
Stack · SpecNext.js, React 19, Tailwind, Prisma/SQLite, Vitest + Testing Library. Spec: docs/superpowers/specs/2026-11-22-pending-transactions-design.html. Mock: ~/Documents/FinanceOS-design-archive/design-mocks/pending-transactions.html (Option A plus the drawer notice).

Global constraints

  • Apply schema changes with npx prisma db push (then npx prisma generate). migrate dev fails on this database (P3006).
  • Only Plaid sync ever sets isPending: true. Manual entries, CSV imports, Teller, Splitwise and split parts always leave it false.
  • When a charge posts, write only externalId, date, amount, importHash and isPending: false. Never touch the merchant, category, confidence, note, tags, trip, outside budget, transfer fields, links or split parts (spec M1, M2).
  • List copy: · Pending, in the same muted text-xs span as · Outside budget. It comes after Outside budget and before the Split label.
  • Drawer copy, exactly: Pending. "The bank may still change the amount or date. Your category, notes and tags will carry over when it posts."
  • Vendor names (Plaid) only in the Plaid sync module. UI copy says "bank".
  • Don't run npm run build while the production server is running. Start a dev server on a free port for the browser check.

Review focus

  1. The "remove pending" message arrives on an earlier page than the posted charge. The row must survive with its edits (Task 2, removalOnEarlierPageStillCarriesOver).
  2. A pending charge is modified while still pending (for example a tip is added). It stays pending, and the "modified" path doesn't clear the flag (Task 1, modifyKeepsPendingFlag).
  3. The pending row was split. After it posts, the parts still point at the same parent (Task 2, postingKeepsSplitParts).
  4. A dry-run preview must not list the taken-over pending ID as "would remove" (Task 2, previewDoesNotRemoveClaimedPending).
  5. A split part of a pending row must not inherit isPending, because nothing would ever clear it (Task 1, splitPartsAreNeverPending).

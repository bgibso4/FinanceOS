Splitwise import

Build the Splitwise card on Settings → Import: drop a group export, import your column at once into the Splitwise account, re-import picks up new, edited and deleted rows, and the result is edited in place with the shared table, drawer and bulk bar, with Restore and Undo.

Review focus

Inputs the spec implies but doesn't spell out, most likely to bite first. Each has a test in its owning task.

  1. The same file imported twice creates nothing and reports everything unchanged. Tests: Task 3 sameFileIsAllUnchanged, Task 5 reimportSameFileCreatesNothing.
  2. A description with a comma in quotes ("Friday Dinner (Feb 13, 2026)") stays one field, and the existing per-account CSV import keeps working on its simple files. Tests: Task 1 quotedCommaStaysOneField, importCsvStillImportsSimpleFile.
  3. A row you deleted yourself never comes back, even when Splitwise later edits it. Tests: Task 5 deletedByYouIsNeverRecreated, editOfDeletedByYouCreatesNothing.
  4. Undo after you edited the imported rows (category, trip) still removes exactly what the import created and puts edited amounts back; Undo of an older import is refused. Tests: Task 6 undoRevertsCreatesEditsAndDeletes, undoRefusedWhenNotLatest.
  5. A failure halfway (e.g. a create throws) leaves the database exactly as before: no transactions, no remembered rows, no import record. Test: Task 5 failureMidImportWritesNothing.

Planning calls

Decisions the spec left to the builder, settled here so every task agrees.

  • P1Two tables
    SplitwiseImport (one per import: account, group, file name, your name, the result shown on the card, and what Undo needs) and SplitwiseRow (one per remembered row of yours: account, group, fingerprint fields, status, optional transaction link with onDelete: SetNull). No change to Transaction except the back-relation.
  • P2Row status
    'imported' | 'skipped' | 'kept' | 'dismissed'. "Deleted by you" is detected as imported with a null link, and persisted as dismissed by the next import.
  • P3Undo by snapshot
    Each import stores, as JSON: the group's remembered rows before it ran, the ids it created, each updated transaction's previous amount and date, and a snapshot of each transaction it deleted (all scalar fields, so Restore and Undo recreate it with the same id). M10 guarantees deleted ones were plain.
  • P4"Reshaped" means
    A transaction is reshaped (M5/M10) when isSplitParent, transferGroupId or linkedTransactionId is set, or it has offsetTransactions. Reshaped edits and deletions are flagged, not applied.
  • P5Category fallback reuses the keyword matcher
    findCategoryBySearchTerms in categorization.ts becomes exported. The Splitwise map (M3) is a map of Splitwise category → search term (Hotel→lodging, Taxi→rideshare, Parking→transportation, Groceries→groceries, Dining out→restaurants, Gas/fuel→gas, Entertainment - Other→entertainment, Sports→sports), confidence 0.72 like a keyword hit. Rules (autoCategorize, incl. its rename) come first.
  • P6Remembered defaults come from the last import
    "Into [account] as [name]" defaults to the latest SplitwiseImport's account and name. With none: the active account whose institution is "Splitwise", and an empty name field (no real name hard-coded in a public repo). No new settings fields.
  • P7Anonymised fixtures
    Three fixtures under tests/fixtures/splitwise/: trip-13_2026-11-08_export.csv (the 13-person trip), trip-pair_2026-11-08_export.csv (the two-person trip) and everyday_2026-11-08_export.csv (the first 40 rows of the everyday group plus its blank line and total row recomputed). People become "Person A…", your column is renamed "Me", names inside descriptions are replaced the same way. Made with a one-off script kept out of git; the source files are in Ben's Downloads (trip-13_…, trip-pair_…, everyday_…).
  • P8One annotate prop on the table
    TransactionTable gains annotate?: (tx: Tx) => ReactNode, rendered under the merchant line. Every other caller ignores it.
  • P9Bulk trip respects split parents
    /api/transactions/bulk gains tripId; it never puts a split parent on a trip (same rule as /api/transactions/[id]) and reports how many it skipped.
  • P10File read in the browser
    As the existing import does: the card reads the file as text and posts { accountId, person, fileName, text, skipBefore? }.

Task 3 · Matcher

  • Files: create src/lib/splitwise/match.ts; test tests/unit/lib/splitwise/match.test.ts.
  • Produces: 
    type RowStatus = 'imported' | 'skipped' | 'kept' | 'dismissed'
type RememberedRow = { id: string; date: string; description: string; cost: number; amount: number; status: RowStatus; transactionId: string | null }
type Pair = { row: RememberedRow; incoming: SplitwiseRow }
type ImportPlan = { unchanged: Pair[]; edited: Pair[]; added: SplitwiseRow[]; vanished: RememberedRow[] }
planImport(remembered: RememberedRow[], incoming: SplitwiseRow[]): ImportPlan
    Algorithm (spec §2): match fingerprints as multisets (each remembered row used once); of the leftovers, group both sides by date|description and pair a group only when it has exactly one remembered and one incoming row (→ edited); everything else left is added / vanished. Task 5 · Import service

  • Files: create src/lib/splitwise/importer.ts, src/lib/splitwise/categories.ts (P5 map), src/lib/splitwise/services.ts; export findCategoryBySearchTerms from categorization.ts; test tests/integration/splitwise/importer.test.ts.
  • Produces: 
    type Categoriser = (row: SplitwiseRow, accountId: string) => Promise<{ categoryId: string | null; confidence: number; merchant: string }>
type RunInput = { accountId: string; person: string; fileName: string; text: string; skipBefore?: string }
type RowNote = { transactionId: string; kind: 'new' | 'changed' | 'payment'; was?: number; cost: number; category: string; flag?: 'check-split' | 'deleted-check' }
type ImportResult = { importId: string; group: string; fileName: string; createdAt: string; firstImport: boolean; canUndo: boolean
  counts: { new: number; payments: number; changed: number; deleted: number; unchanged: number; skippedByDate: number; others: number; otherCurrency: number; ignored: number; needCategory: number }
  notes: RowNote[]; transactions: Tx[]        // created/changed/flagged, TX_ROW_INCLUDE shape, newest first
  deleted: { rowId: string; date: string; description: string; amount: number; category: string | null; restored: boolean }[]
  others: { date: string; description: string; cost: number }[]; total: number }
class SplitwiseImporter { constructor(store: SplitwiseStore, categorise: Categoriser)
  run(input: RunInput): Promise<ImportResult>; result(importId: string): Promise<ImportResult>
  defaults(): Promise<{ accountId: string | null; person: string; knownGroups: string[] }>
  isKnown(accountId: string, group: string): Promise<boolean> }
  • run in one store transaction: group from file name (none → SplitwiseExportError); read export; load remembered rows; persist imported + null link as dismissed; plan; then
    • unchanged: nothing.
    • edited: imported + live + not reshaped → update transaction amount, date (record before-values) and the row's fingerprint; reshaped → row fingerprint only, note flag check-split; other statuses → row fingerprint only.
    • added: currency ≠ account currency → count otherCurrency, not stored; first import with skipBefore and date < it → row skipped; else create the transaction (merchant/date/amount, account, Payment → isTransfer: true, no category, confidence 1; otherwise the categoriser: autoCategorize then the P5 fallback; importHash via createImportHash) and row imported.
    • vanished: imported + live + not reshaped → snapshot, delete transaction, delete row, add to deleted; reshaped → row kept, note flag deleted-check; other statuses → delete row.
    • Save the import with result and P3 undo; return the result (transactions loaded with TX_ROW_INCLUDE; canUndo true).
